# Phase 3: personal search preferences and onboarding

Search preferences are self-stated data, separate from verified candidate profiles used in résumé generation. They do not change vacancy ingestion, ranking, scores, notifications or application behavior. The beta catalogue remains neutral.

## Persistence and API

V18 adds `search_profile_revisions` and `search_profile_state`. Revisions are keyed by candidate/revision, with candidate/request-ID uniqueness. The active pointer has a composite candidate/revision FK. PostgreSQL rejects revision updates/deletes. A candidate row lock serializes creation and activation in one transaction, including the first profile. The service revalidates sessions before private access and after taking the lock. No frontend candidate ID is accepted.

`GET /api/mini-app/v2/me/search-profile` uses the existing bearer session and returns `{activeRevision, profile, completionStatus, missingRequiredFields, createdAt}` with no-store caching. Revision 0 has no stored profile and `createdAt: null`. Completion is NOT_STARTED, INCOMPLETE or COMPLETE. Required for completion: desired titles or role categories, target countries/regions, and work formats. Other fields may remain explicitly unknown or unstated. Incomplete revisions can be stored through the API and still require onboarding.

`PUT` at the same path accepts `{expectedRevision, requestId, profile}`. The revision is a nonnegative integer; the request ID is 8–64 ASCII letters/digits/underscore/hyphen. Do not reuse a request ID for a changed payload. Repeating an identical current request returns its existing revision/timestamp. A stale expected revision, reused key with a changed payload, or replay of an older superseded request returns `409 SEARCH_PROFILE_CONFLICT`; none reactivates old data. Malformed/unknown properties, wrong JSON types, numeric enum ordinals, invalid enums and field bounds return `400 INVALID_SEARCH_PROFILE`. Authentication preserves existing 401/403/503 contracts. Timestamp/revision/completion are server-owned.

The profile carries desiredTitles, roleCategories, industries, technicalSkills, nontechnicalSkills, experienceLevel, statedExperience, experienceYears, currentCountry, currentCity, targetRegions, workFormats, employmentTypes, languages, workAuthorization, authorizationDetails, salary, education, studentStatus, relocation and additionalPreferences. Lists are bounded (40 text entries, 20 languages); text entries are 120 characters, narrative fields 1,000–2,000. Experience is explicitly self-stated (0–80 years if supplied). Languages carry a language name and UNKNOWN/A1/A2/B1/B2/C1/C2/NATIVE proficiency. Work authorization defaults only to UNKNOWN and can be AUTHORIZED, REQUIRES_SPONSORSHIP or NOT_AUTHORIZED, with self-stated country details. Salary is either null or a positive amount (at most 1,000,000,000; two decimal places), valid ISO currency and HOUR/DAY/WEEK/MONTH/YEAR period. No names, phones, institutions or résumé uploads are required.

`GET /me` keeps its fields and reports READY/onboardingRequired=false only for a complete active profile; otherwise ONBOARDING_REQUIRED/true. Legacy owner workspace access does not depend on onboarding. Global candidate bootstrap remains unchanged.

## Mini App

Beta users see five mobile questionnaire/review steps before their candidate-scoped workspace. Completed profiles load from the server; users can reopen the editor later. The owner retains the original workspace and can opt into preferences with its v2 session. Each review shows every selection and unknown state, plus an explicit notice that preferences do not affect ranking yet.

Drafts stay in component memory through step navigation, validation and network errors, and clear on account replacement/expiry. Credentials and drafts are never stored in localStorage/sessionStorage. Reload requires a fresh Telegram launch under the existing one-use launch contract, then restores confirmed preferences. Save taps are coalesced; ambiguous results retain the same request ID for a manual retry. A conflict preserves the draft, disables saving and offers an explicit reload of the latest confirmed profile. Late loads/saves are checked against their original account generation and cannot invalidate or retry into another account.

## Recovery and release boundary

The preserved Phase 2.5 V17 image/evidence is immutable and is **not** compatible with V18. Its verified durable copy is recorded in the Phase 3 preservation manifest outside this checkout. Never use it as a V18 rollback target, bypass Flyway validation, remove profiles/workflows, or rewrite applied migrations.

This Phase 3 runtime requires exact validated V18 in normal and recovery modes. Disabled Flyway fails startup; unknown V19 or incompatible history fails before context refresh. The recovery profile targets V18 and retains the prior closed-beta/no-poller/no-sends/no-scheduler safeguards. A transactional failed future migration leaves V18 recoverable; a committed future migration requires a separately tested forward corrective binary or coordinated restore, never destructive downgrade.

Use `scripts/build-recovery-artifact.py verify --output <new durable private directory>` with Java 21, Node 22, working local Docker and existing tool caches. It excludes environment/key files, snapshots tracked/nonignored source, runs full Java/PostgreSQL/frontend verification, builds the exact API frontend into the JAR and writes hash evidence. `image --verification <proof> --base-image <resolved immutable Alpine JRE21 digest>` creates/saves a **local-only** V18 recovery image. Do not publish it. `RecoveryImageRehearsal` accepts its manifest, a private evidence directory, and the preserved V17 manifest; it exercises actual V13→V18 startup, independent owner/beta workflows and profile histories, failed release, V17 refusal, V18 recovery/resumption, unstubbed browser onboarding/reload, and unknown V19 refusal.

Production remains **NO-GO**. A green local rehearsal does not verify managed Azure restore/PITR, document checkpoint coordination, TLS/networking/permissions/capacity, actual owner identity, Caddy route allowlists or single-poller operations. The prior release runbook still applies operationally, with V18 replacing the candidate-aware recovery boundary and exact GET/PUT search-profile routes added to a separately reviewed proxy plan. No Caddy changes or production access are part of this work.

Final exact source paths, pass/fail/skip counts, independent findings/fixes, checksum comparisons and saved-image hashes are recorded in the durable Phase 3 final verification report; source is frozen before artifact verification so subsequent evidence cannot silently change its identity.
